# AI Desktop Autopilot (MCP + Overlay Daemon)

Автономная система компьютерного зрения и физического ввода для LLM-агентов. Оснащена визуальным HUD-оверлеем на PyQt6, аппаратной защитой от попадания в скриншоты (`WDA_EXCLUDEFROMCAPTURE`), визуальной координатной сеткой и бесконфликтным детектором физического вмешательства человека.

---

## Архитектура системы

Проект разделен на два изолированных процесса, взаимодействующих по локальному WebSocket (`ws://127.0.0.1:8765`):

```text
ai-autopilot-mcp/
├── config.py             # Настройки геометрии, таймаутов, портов и Per-Monitor DPI
├── overlay_ui.py         # Полноэкранный HUD-оверлей PyQt6 (аппаратное скрытие WDA_EXCLUDEFROMCAPTURE)
├── input_controller.py   # Низкоуровневые хуки Win32 (WH_MOUSE_LL / WH_KEYBOARD_LL), SendInput
├── vision_engine.py      # Захват mss, координатная сетка (100px/50px), перцептивная стабилизация, pywinauto
├── autopilot_daemon.py   # Фоновый сервер: qasync (PyQt6 + asyncio WebSocket), трей
├── mcp_server.py         # MCP-шлюз (MCPServer из mcp 2.x) для подключения к LLM
├── pyproject.toml        # Метаданные пакета, закреплённые зависимости, точки запуска
├── requirements.txt      # Зависимости Python (дублирует pyproject для pip -r)
├── tests/                # Регрессионные тесты чистой логики
├── docs/                 # ADR, глоссарий и план развития
├── install.bat           # Создание .venv и установка зависимостей
├── start_daemon.bat      # Скрипт быстрого запуска фонового демона
├── mcp_config.example.json # Пример конфигурации MCP для Claude Desktop, Cursor, Gemini
└── kilo.json.example       # Пример конфигурации для Kilo (другой формат: секция mcp)
```

## Быстрый старт на новом устройстве

### 1. Требования
- ОС: Windows 10 версии 2004 и новее, либо Windows 11 (64-bit).
  `WDA_EXCLUDEFROMCAPTURE` появился только в 2004.
- Python 3.11, 3.12 или 3.13, добавленный в `PATH`.
  Минимум 3.11 обязателен: `config.py` использует `enum.StrEnum`.

### 2. Установка зависимостей
Запустите `install.bat` — он создаст виртуальное окружение `.venv` и установит
проект в редактируемом режиме. То же самое вручную:
```powershell
python -m venv .venv
.venv\Scripts\python.exe -m pip install -e ".[win32]"
```

Установка даёт две точки запуска вместо обращения к файлам скриптов:
`.venv\Scripts\autopilot-daemon.exe` и `.venv\Scripts\autopilot-mcp.exe`.

Зависимости закреплены в `pyproject.toml` с верхними границами: проект работает
с нативными API Windows и чувствителен к смене мажорных версий SDK. В частности,
требуется `mcp>=2.0,<3` — в mcp 2.x модуль `mcp.server.fastmcp` удалён, и код,
рассчитанный на `FastMCP`, не запустится.

Для проверки:
```powershell
.venv\Scripts\python.exe -m pytest tests -q
.venv\Scripts\ruff.exe check .
```

### 3. Запуск демона оверлея
Запустите `start_daemon.bat`. В трее появится иконка агента, а в консоли отобразится статус запуска WebSocket-сервера.

## Подключение к LLM-клиентам (MCP)

Во всех примерах используется точка запуска из `.venv`, поэтому интерпретатор и
состав зависимостей не зависят от того, что установлено в системе. Замените
`C:\path\to` на реальный путь к проекту.

> [!IMPORTANT]
> Не указывайте пустой объект `"env": {}` в конфигурации на Windows. Это стирает
> переменные среды `SystemRoot` и приводит к сбою загрузчика DLL.

### Kilo
Формат Kilo **отличается** от остальных разделов: секция называется `mcp`, а не
`mcpServers`, и `command` — это массив, а не строка. Файл — `kilo.json`/`kilo.jsonc`
в корне проекта либо `~/.config/kilo/kilo.jsonc` глобально; глобальный вариант
уместнее, потому что автопилот управляет рабочим столом, а не одним проектом.
Готовый пример с комментариями — в [`kilo.json.example`](kilo.json.example).

```jsonc
{
  "mcp": {
    "desktop-autopilot": {
      "type": "local",
      "command": [
        "C:\\path\\to\\ai-autopilot-mcp\\.venv\\Scripts\\autopilot-mcp.exe"
      ],
      "enabled": true,
      "timeout": 120000
    }
  }
}
```

Таймаут указывается в миллисекундах и **по умолчанию равен 5000**. Его нужно
поднять: `get_ui_elements` обходит дерево доступности и по таблице таймаутов проекта
может занимать до 90 с, `wait_terminal` и `wait_for_text` ждут условие до 30 с. С
умолчательными пятью секундами инструменты падали бы по времени, а не по существу.

Разрешения на инструменты MCP задаются ключом `{сервер}_{инструмент}`; правила
читаются сверху вниз, и последнее совпавшее побеждает. В `kilo.json.example`
наблюдения разрешены, а шесть изменяющих инструментов (`mouse_action`,
`keyboard_action`, `scroll_screen`, `act_on_element`, `window_action`,
`write_terminal`) оставлены на подтверждении. Для полностью автономной работы
широкое правило заменяется на `"desktop-autopilot_*": "allow"`.

После правки конфига Kilo нужно перезапустить: серверы MCP читаются при старте.
Проверить подключение можно через `ctrl+p` → MCP или команду `/mcps`.

### Claude Code
```powershell
claude mcp add desktop-autopilot -- "C:\path\to\ai-autopilot-mcp\.venv\Scripts\autopilot-mcp.exe"
```

## Справочник инструментов (Tools API)

Всего 23 инструмента. Описания инструментов, которые видит модель, на английском;
строки, возвращаемые человеку, на русском.

Во всех инструментах, возвращающих снимок, координаты указываются **в масштабе
кадра**, а не в физических пикселях: ширина кадра всегда 1280, высота
пропорциональна монитору. Демон пересчитывает их сам с учётом Per-Monitor DPI.

Каждый успешный ответ содержит блок `session`. Если рабочая станция
заблокирована, захват экрана всё равно выполняется и возвращает экран блокировки,
поэтому в тексте инструмента первой строкой выводится предупреждение — иначе
кадр экрана блокировки неотличим от кадра целевой программы.

### `list_windows_and_monitors()` -> `str`
Список мониторов и открытых окон. Для каждого окна возвращаются `handle`, класс
Win32, pid, границы, индекс монитора и признак `on_monitor`. Индекс 0 — это весь
виртуальный стол, а не отдельный экран. `on_monitor=False` означает, что центр
окна попал в зазор между мониторами и индекс приблизительный.

### `take_control(monitor_index=None, show_grid=False)` -> `list[Image | TextContent]`
Захватывает сессионное управление, включает непрерывную неоновую рамку HUD на
целевом экране и возвращает первый стабилизированный снимок. Вызывается первым
шагом перед интерактивными действиями.

`monitor_index=1` — основной монитор, `0` — все экраны как один виртуальный стол,
`None` — автовыбор. Неверный индекс возвращает ошибку со списком доступных, а не
молчаливый откат: откат на 0 меняет масштаб кадра и обесценивает все накопленные
координаты.

### `release_control()` -> `str`
Освобождает управление и гасит рамку HUD. Вызывается в конце всей составной
задачи. Доступен и в состоянии `USER_OVERRIDE` — иначе пауза оставляла рамку
горящей без выхода.

### `get_screen_state(monitor_index=None, show_grid=False)` -> `list[Image | TextContent]`
Свежий снимок, статус системы (`IDLE`, `AI_ACTIVE`, `USER_OVERRIDE`), разрешение
кадра и позиция курсора. Если курсор находится на другом мониторе, `cursor`
равен `null`, а реальная позиция на рабочем столе возвращается отдельно —
отрицательная координата «внутри кадра» была бы бессмысленной.

### `get_ui_elements(window_title=None, monitor_index=None, hwnd=None, class_name=None)` -> `str`
Сканирует интерактивные элементы окна через UI Automation и возвращает готовые
координаты `click_target: [x, y]` в масштабе кадра.

Заголовок сам по себе окно не определяет: у приложения может быть несколько окон
верхнего уровня с одинаковым заголовком (основное плюс уведомления). Ответ всегда
сообщает, какое окно выбрано и каким способом: `hwnd`, `unique`, `largest-of-N`,
`win32-title` или `foreground`. Чтобы исключить угадывание, передавайте `hwnd`.

Элементы вне указанного монитора не возвращаются с отрицательным `click_target`,
а учитываются в `skipped_off_monitor`. Пустой список отличим от неверно
выбранного окна: если окно не найдено, возвращается ошибка.

### `probe_target(hwnd=None, window_title=None, class_name=None)` -> `str`
Определяет, какой путь управления цель поддерживает, **до** выбора пути. Возвращает
классификацию (`terminal`, `rich`, `partial`, `opaque`, `expensive`), инвентарь
паттернов внутри цели, измеренную стоимость узла в микросекундах, число узлов в
пробном обходе, признак свёрнутости и конкретную рекомендацию.

Классификация строится на пробном обходе, а не на числе элементов первого уровня:
у Chromium и Electron над настоящим деревом стоит цепочка представлений в 4–6
уровней, поэтому окно с двумя детьми на первом уровне отдаёт сотни полезных узлов.
Стоимость узла измеряется, потому что между целями она различается в 100 раз.

### `get_snapshot(hwnd=None, window_title=None, class_name=None, monitor_index=None, max_nodes=None, max_depth=None, time_budget_ms=None, token=None, auto_restore=False)` -> `str`
Основной путь наблюдения: ограниченный семантический снимок дерева доступности.
Не занимает курсор, работает по неактивным и перекрытым окнам, не зависит от
масштаба кадра. Координаты приводятся к кадру снимка.

Снимок намеренно неполон на больших целях. Заголовок сообщает, какой лимит
сработал, и для лимитов времени и числа узлов даёт токен продолжения; усечение по
глубине токеном не продолжается — увеличьте `max_depth`. Бюджет времени является
основным ограничителем: стоимость узла между целями различается в 100 раз
(217 мкс на одной странице браузера, 16,9 мс на другой), поэтому потолок по числу
узлов предохранителем не является.

Пределы по умолчанию: `time_budget_ms` 150, `max_nodes` 400, `max_depth` 40.
Глубина была 20 и поднята после замера Firefox, чья страница профиля уходит на
уровень 23, а видео — на 26: при 20 снимок обрывался терминально, без токена и
без возможности дочитать.

Строка снимка: `путь [роль] 'текст' @x,y {паттерны}`. Путь — устойчивый адрес по
индексам среди соседей; именно его принимает `resolve_clickable`. Текст с пометкой
`[по классу]` — имя класса элемента, а не содержимое интерфейса.

### `resolve_clickable(path, hwnd=None, window_title=None, class_name=None, monitor_index=None)` -> `str`
Точная точка клика для одного узла снимка. Снимок несёт центр прямоугольника,
потому что собственный запрос точки у UIA — живой вызов стоимостью 162 мкс на узел
(26% обхода). Разрешать точечно дешевле, а результат свежее. Возвращает отказ, а
не устаревшую координату, если элемент вне экрана, окно свёрнуто или путь больше
не разрешается.

### `act_on_element(action, path, text=None, value=None, hwnd=None, window_title=None, class_name=None, dry_run=False, allow_host_input=False)` -> `str`
Действует на узел снимка через паттерн UIA, **не занимая курсор**. Это путь Класса B:
окно не обязано быть активным или видимым, и человек может продолжать работать.
Предпочтительнее `mouse_action` и `keyboard_action` всегда, когда паттерны узла это
позволяют.

- `action`: `invoke`, `set_value` (требует `text`), `toggle`, `select`, `expand`,
  `collapse`, `scroll_into_view`, `focus`, `set_range_value` (требует `value`).
- `path`: путь узла из `get_snapshot`, например `1.0.2`.

`scroll_into_view` закрывает разрыв между наблюдением и действием: снимок помечает
узлы признаком «за пределами видимой области», но до появления глагола привести их в
вид можно было только эскалацией в Класс A и прокруткой пикселями. Подтверждается
через `IsOffscreen` — то же свойство, которое снимок публикует, поэтому действие и
наблюдение пользуют одно определение видимости.

`set_range_value` отказывает значению вне диапазона элемента вместо обрезания.
Провайдер записал бы ближайшую границу и перечитал её, поэтому перечитывание
подтвердило бы число, которого вызывающая сторона не запрашивала, — та же молчаливая
подстановка, которая уже устранена в слое ввода.

`focus` подтверждается через `HasKeyboardFocus`, потому что именно это свойство
решает, куда ляжет вводимый текст, а не координата каретки.

Каждое действие подтверждается перечитыванием состояния, кроме `invoke`: у него нет
собственного состояния, и результат честно сообщается как «вызов принят, эффект не
проверен». Отдельный статус «НЕ ПОДТВЕРЖДЕНО» означает, что вызов прошёл, а
состояние не изменилось — это реальный отказ, а не теория: у терминала
`ValuePattern.SetValue` сообщает `IsReadOnly=0`, принимает вызов и ничего не меняет.

Перечитывание опрашивает состояние, а не читает его один раз. Состояние UIA
обновляется не синхронно с вызовом: на живом Qt-списке `Expand` вернул успех, а
немедленное чтение всё ещё показывало `Collapsed`; через несколько сотен
миллисекунд оно показывало `Expanded`. Однократное чтение дало бы ложный отказ, и
агент повторил бы уже сработавшее действие — а повтор на переключателе его отменяет.

### `window_action(action, hwnd=None, window_title=None, class_name=None, x=None, y=None, width=None, height=None, dry_run=False, allow_host_input=False)` -> `str`
Действует на окно целиком через UIA, **не занимая курсор и не забирая фокус**.
Класс B, поэтому работает по неактивному и перекрытому окну и не мешает человеку.

- `action`: `restore`, `minimize`, `maximize`, `close`, `move` (требует `x`, `y`),
  `resize` (требует `width`, `height`), `activate`.

Два из этих действий — предусловие наблюдения, а не удобство. Свёрнутое окно
захватывается чёрным кадром, неотличимым от пустого, поэтому `restore` вызывается
перед любым снимком. А окно, оставшееся открытым после неудачного `close`, обычно
держит модальный диалог, который агенту придётся закрыть прежде, чем двигаться
дальше.

`close` подтверждается исчезновением дескриптора, а не возвратом вызова: `Close`
просит приложение закрыться, и приложение с несохранёнными изменениями вместо этого
покажет диалог и останется открытым. Сообщить успех по возврату вызова значило бы
сказать агенту, что окна нет, пока поверх него ждёт ответа модальное окно.

`move` и `resize` сверяются с прямоугольником окна с допуском в несколько пикселей:
`Transform` позиционирует ограничивающий прямоугольник, а часть менеджеров окон
размещает клиентскую область со сдвигом на ширину рамки. Окно, сообщающее
`CanMove=0` или `CanResize=0`, отказывает вместо того, чтобы отчитаться о
несостоявшемся изменении.

`activate` выводит окно на передний план. Замер (спайк S7): из фонового процесса
голый `SetForegroundWindow` не сработал ни разу из двух и даже не вернул «да», а с
`AttachThreadInput` сработал 2 из 2 за 15 мс. Подтверждение идёт через
`GetForegroundWindow`, потому что возврат вызова ненулевой и тогда, когда он лишь
подсветил кнопку на панели задач. Свёрнутое окно отказывает с указанием на
`restore`: активация не разворачивает его, а успех описал бы окно, которое всё ещё
является значком.

### `read_terminal(hwnd=None, window_title=None, class_name=None, tail=200, head=None, start=None, count=None, contains=None)` -> `str`
Читает буфер консоли напрямую через `TextPattern`. Работает с Windows Terminal и
legacy conhost. Текст возвращается точно, включая кириллицу, а не как распознанные
глифы; OCR и снимок экрана не нужны. Чтение — Класс B: работает по свёрнутому и
перекрытому терминалу и не мешает человеку.

Возвращается **весь буфер экрана**, а не видимая область: замерено 9000 строк, около
1,1 МБ, за 30 мс. Это слишком много для ответа, поэтому выбирается срез — по
умолчанию последние 200 строк, где лежит результат последней команды.

Буфер является кольцом высотой около 9000 строк. За её пределами самый старый вывод
теряется безвозвратно, и ответ сообщает `buffer_full`. Для долгой команды буфер надо
читать по мере поступления вывода, а не один раз в конце.

Строки приходят дополненными пробелами до ширины консоли и обрезаются справа;
отступы слева сохраняются, потому что они содержательны.

### `write_terminal(text, hwnd=None, window_title=None, class_name=None, enter=True, expect=None, timeout_s=3.0, allow_host_input=False)` -> `str`
Печатает в консоль, **не занимая клавиатуру и курсор** — Класс B, работает параллельно
с вашей работой. Символы посылаются как `WM_CHAR` в то окно, которое консоль
действительно использует для ввода: у Windows Terminal это дочернее окно XAML-island
(`Windows.UI.Input.InputSite.WindowClass`), а не окно верхнего уровня; у conhost —
само окно верхнего уровня.

Каждая запись подтверждается перечитыванием буфера. Это обязательно: `ValuePattern` у
терминала сообщает `IsReadOnly=0`, принимает `SetValue` и ничего не меняет. Запись без
перечитывания не считается состоявшейся.

`expect` по умолчанию равен самому тексту, что верно для оболочки с эхом ввода. При
подавленном эхе (ввод пароля) передайте пустую строку — проверка вырождается в
«буфер изменился» и сообщается как слабая.

### `wait_terminal(expect, hwnd=None, window_title=None, class_name=None, timeout_s=30.0, interval_s=0.25, after_text=None)` -> `str`
Ждёт появления текста в буфере консоли вместо сна на фиксированное время. Возвращается
сразу, как только текст появился, и прямо сообщает, если не дождался.

`after_text` важнее, чем выглядит. Оболочка печатает командную строку до исполнения,
поэтому ожидание строки, входящей и в команду, срабатывает мгновенно по эху и ничего
не доказывает. Замерено: ожидание маркера из `ping -n 7 ... & echo MARKER` вернуло
успех за **0,00 с**, а то же ожидание с `after_text` заняло **6,16 с** и совпало с
настоящим выводом. Передайте набранную команду — поиск начнётся после неё. Инструмент
дополнительно предупреждает, когда ожидание вернулось быстрее 50 мс.

### `find_text_on_screen(text, monitor_index=None, fuzzy=True)` -> `str`
Находит текст на экране через OCR и возвращает координаты в пространстве кадра — их
можно передавать в `mouse_action` напрямую.

Это **запасной путь** для целей без дерева доступности: содержимое Проводника, Java
AWT, canvas-поверхности. Если дерево есть, `get_snapshot` и `act_on_element` точнее,
дешевле и дают семантику.

Распознавание выполняется на **нативном разрешении**, а не на сжатом кадре для модели,
и это не мелочь. Замер одного экрана в разных масштабах: нативный 1920×1080 дал 76
строк и 2555 символов, сжатие до 1280 — 51 строку и 1358 символов с видимой порчей
текста, а для виртуального рабочего стола 4480→1280 распознавание вернуло **ноль
строк**. Апскейл сжатого кадра возвращает большую часть, но не всё. Подробности и
таблица замеров — в ADR-0011.

Сопоставление нормализует регистр, свёртывает кириллические и латинские омоглифы и
отбрасывает пунктуацию: русскоязычный распознаватель читает латинские надписи
кириллическими похожими буквами, а подчёркивания теряет. Без нормализации обычный
поиск подстроки сообщает «не найдено» для текста, который виден на экране.

**Отсутствие совпадения не доказывает отсутствие текста.** Распознаватель подменяет
отдельные буквы, и нормализация это не исправляет. При промахе инструмент прямо об
этом говорит и предлагает сократить строку или прочитать экран целиком.

### `read_screen_text(monitor_index=None, limit=120, with_words=False)` -> `str`
Читает весь распознанный текст экрана с рамками. Для непрозрачной цели это
единственный способ увидеть содержимое как текст, а не как пиксели. Это же способ
диагностировать неудачный `find_text_on_screen`: видно, что распозналось на самом
деле — текста нет или он прочитан с ошибками.

### `wait_for_text(text, monitor_index=None, timeout_s=20.0, interval_s=0.75, appear=True, fuzzy=True)` -> `str`
Ждёт появления текста на экране (или его исчезновения при `appear=False`) вместо сна
на угаданное время. Возвращается сразу, как только условие выполнено, и прямо
сообщает, если не дождался.

Опрос крупнее, чем у `wait_terminal`, потому что каждый проход захватывает и
распознаёт кадр, а не читает буфер. Тот же caveat про подмену букв: ждать длинную
уникальную строку рискованно, лучше короткий устойчивый фрагмент.

### `wait_for_event(condition=None, quiet_ms=None, hwnd=None, window_title=None, timeout_s=30.0, since_tick=None, events=None)` -> `str`
Ждёт событий интерфейса вместо поллинга кадрами. Дешевле `wait_for_text` и
`wait_terminal`: не захватывает кадр и не распознаёт текст, но видит факт изменения, а
не его содержимое.

Два режима. `condition` ждёт, пока что-то произойдёт; `quiet_ms` ждёт, пока интерфейс
перестанет меняться. После действия второй подходит лучше, потому что не требует
угадывать, какое именно событие испустит конкретный контрол.

- `condition`: `opened`, `closed`, `focused`, `value_changed`, `tree_changed`,
  `appeared`.
- `events`: сырые коды WinEvent, если ни одно условие не подходит.
- `hwnd` / `window_title`: ограничить одним окном. Совпадение идёт по всему окну
  верхнего уровня, а не только по его рамке: события от контролов несут дескриптор
  контрола.
- `since_tick`: метка, от которой считать. Без неё берётся момент вызова. События
  старше метки отбрасываются и сообщаются как `discarded_stale`, а не как совпадение:
  недоставка накапливается, а не исчезает, и пачка старых изменений не должна читаться
  как «интерфейс только что изменился».

Таймаут приходит отчётом с `matched=false`, а не статусом ошибки: то, что ничего не
произошло, — нормальный исход ожидания.

Ожидание живёт на отдельном потоке с собственным насосом сообщений Win32, потому что
`WINEVENT_OUTOFCONTEXT` доставляет колбэк в очередь того потока, который зарегистрировал
хук. На рабочем потоке действия результат не «медленно», а ноль событий и ни одной
ошибки.

Тот же поток обслуживает стабилизацию кадра после действий Класса A: вместо серии
захватов до settling'а перцептивной разности демон ждёт тишины в потоке событий и
снимает один кадр. Замер на рабочей машине — 125 мс против 273 мс, без единого захвата
во время ожидания. Если наблюдатель не запустился или действию нечего сообщить как
метку, путь автоматически откатывается к разности кадров.

### `execute_batch(steps, hwnd=None, window_title=None, class_name=None, stop_on="both", observe_at_end=True, monitor_index=None)` -> `list[Image | TextContent]`
Исполняет последовательность шагов Класса B одним вызовом и возвращает **одно**
наблюдение в конце. Восемь шагов стоят одного захвата кадра, а не восьми.

Каждый шаг — глагол `act_on_element` или `window_action`, адресуемый через `path`
относительно окна, которое разрешил пакет:

```json
{"kind": "element", "action": "set_value", "path": "3.1.0", "text": "значение"}
{"kind": "window",  "action": "restore"}
```

Шаги Класса A (`mouse_action`, `keyboard_action`, `scroll_screen`) **отклоняются**, а не
исполняются по одному. Правильный пакет из них требует одной транзакции захвата канала
ввода на весь пакет, а этот механизм по замеру S9 недоступен из неповышенного процесса.
Исполнять их пошагово внутри того, что называется пакетом, значило бы заявлять
атомарность, которой нет.

`stop_on` — где пакет останавливается: `failure` (шаг не подтвердился), `high_risk`
(шаг классифицирован как непакетируемый, остановка **до** исполнения), `both` (то и
другое, по умолчанию). Значения `never` нет намеренно: оно исполнило бы необратимый шаг
внутри пакета без возможности остановиться.

Предполётная проверка читает фактическое состояние цели до исполнения шага и сверяет с
объявленным:

```json
{"action": "invoke", "path": "3.1",
 "assert": {"path": "0.5", "name_contains": "Alice"}}
```

Расхождение прерывает пакет и возвращает **обе** величины — объявленную и прочитанную, —
потому что одно лишь «проверка не прошла» не даёт отличить устаревший путь от
действительно неверного адресата, а реагировать на них нужно противоположным образом.

Шаги идут через тот же код, что и одиночные действия, поэтому каждый получает ту же
защиту от ввода в дерево хоста, тот же уровень риска и тот же dry-run. Ответ сообщает
уровень, в который разрешился каждый шаг: это и есть признак промаха — путь, попавший на
«Отправить» вместо «Отмена», возвращается как необратимый.

`executed` и `succeeded` — разные числа. Исполненный, но не подтвердившийся шаг всё
равно исполнен, а остановленный до исполнения — нет; один счётчик на оба сделал бы
«исполнено» неоднозначным ровно в том случае, когда вызывающей стороне нужно понять,
сколько пакета действительно произошло.

### `mouse_action(action, x, y, end_x=None, end_y=None, monitor_index=None, show_grid=False)` -> `list[Image | TextContent]`
Действие мышью с предиктивной подсветкой цели за 250 мс до клика. Это действие
Класса A: оно занимает единственный курсор сессии и не может выполняться
одновременно с работой человека.
- `action`: `"click"`, `"double_click"`, `"right_click"`, `"move"`, `"drag"`.
- `x`, `y`: координаты в масштабе кадра.

Ответ сообщает, где курсор оказался фактически, а не куда его просили переместить:
расхождение и есть признак несработавшего клика.

### `keyboard_action(text=None, hotkey=None, monitor_index=None, show_grid=False)` -> `list[Image | TextContent]`
Ввод текста или нажатие комбинации. Тоже Класс A.
- `text`: вводится посимвольно через `KEYEVENTF_UNICODE`, а не вставкой из буфера
  обмена. Раскладка RU/EN не влияет, буфер пользователя не затрагивается, ввод
  работает там, где `Ctrl+V` не является вставкой. Буфер используется как
  запасной путь только для текста длиннее порога и разрушает нетекстовые форматы.
- `hotkey`: сочетание клавиш (`"ctrl+s"`, `"alt+tab"`, `"enter"`, `"esc"`).

### `scroll_screen(direction="down", amount=3, x=None, y=None, monitor_index=None, show_grid=False)` -> `list[Image | TextContent]`
Прокрутка колесом мыши с ожиданием стабилизации изображения. Класс A. Поддерживается
только вертикальное направление.

### `reset_user_override()` -> `str`
Немедленно возвращает управление агенту: сбрасывает `USER_OVERRIDE` в `IDLE`.
Обычно не нужен — пауза снимается сама после `IDLE_RESUME_SECONDS` (5 с) без
физического ввода, — но полезен, когда известно, что человек отошёл, и ждать
порог незачем. Тот же эффект у `take_control`, который вдобавок возвращает кадр
и явно сообщает, что управление отобрано после перехвата.

### `get_hud_state()` -> `str`
Живая геометрия оверлея HUD: границы окна, обрамляемая область в глобальных и
локальных координатах, точка фактической отрисовки и признак корректности. Оверлей
аппаратно исключён из скриншотов (`WDA_EXCLUDEFROMCAPTURE`), поэтому неверно
расположенную рамку на снимке не увидеть — это единственное проверяемое
свидетельство её положения.

## Защита от конфликта с пользователем

Демон перехватывает физические движения мыши и нажатия клавиш на уровне Windows
Low-Level Hooks:

1. Если человек сдвинул мышь более чем на 15 пикселей во время работы агента,
   текущее действие немедленно обрывается и не доигрывается.
2. Неоновая рамка меняет свечение на янтарно-желтое.
3. Агент получает статус `interrupted` и текст `PAUSE` с фактическим порогом
   авто-снятия.
4. Пауза снимается сама после `IDLE_RESUME_SECONDS` (5 с) подряд без
   физического ввода — измеряется через `GetLastInputInfo`, который считает и
   движение мыши, поэтому неподвижность означает именно неподвижность.
   Порог задаётся в `config.py`; ноль возвращает прежнее поведение, при котором
   пауза снимается только явно.
5. `Ctrl + Alt + Space` на физической клавиатуре снимает паузу немедленно, со
   стороны человека.

Перехват остаётся взведённым и после авто-снятия: любое новое движение мыши снова
приостанавливает агента. Пауза, следовательно, не лишает человека управления, а
устраняет тупик, в котором выход требовал реплики в чате.

Пауза не является тупиком и для агента: наблюдательные инструменты
(`get_screen_state`, `list_windows_and_monitors`, `get_ui_elements`,
`get_snapshot`, `probe_target`, `resolve_clickable`, `read_terminal`,
`wait_terminal`, `read_screen_text`, `find_text_on_screen`, `wait_for_text`,
`get_hud_state`) и три действия над состоянием (`take_control`,
`release_control`, `reset_user_override`) остаются доступными.

Заблокированы действия Класса A, занимающие курсор и клавиатуру
(`mouse_action`, `keyboard_action`, `scroll_screen`), и изменения состояния
приложений через Класс B: `act_on_element`, `window_action` и `write_terminal`.
Последние намеренно — они не трогают курсор, но меняют окно, в которое человек,
только что взявший машину, может печатать, или перемещают окна, которые он сам
расставил.

## Слой безопасности (ADR-0012)

Демон исполняет три вещи вокруг каждого мутирующего действия.

**Отказ во вводе в собственное дерево процессов хоста.** Шлюз присылает свой PID с
каждым запросом, демон обходит дерево от него сам — список от клиента не
принимается, потому что неполный список это защита с дырами. Защищены процесс
хоста, его предки до первой инфраструктурной программы ОС и все их потомки: это
покрывает окна, которые рисуют разговор, и оболочки, которые хост порождает для
своего канала инструментов. Оболочка (`explorer.exe`) в набор не входит — иначе
защита отказала бы в клике по пустой области рабочего стола. Терминал, запущенный с
рабочего стола, приходится потомком оболочки и остаётся автоматизируемым.

Отказ приходит статусом `refused`, а не `error`: ошибка приглашает повторить с
другими параметрами, отказ говорит, что цель вне досягаемости. Инструменты,
адресующие окно явно, принимают `allow_host_input`, и переопределение пишется в
трейс. Координатные действия его не принимают вовсе — ничто в таком запросе не
говорит, куда попадёт точка.

**Классификация уровня риска.** `reversible`, `medium` или `irreversible` — по имени
того элемента, в который разрешился путь, а не по названному глаголу. Промах на один
элемент не виден ни одной проверке, которая доверяет запросу, и виден той, которая
читает разрешённый элемент. Матчинг по русским и английским основам, с границами
слова: подстрочный поиск для `drop` классифицировал бы каждый `Dropdown` как
необратимый. Политика только ужесточает.

**Трейс.** `logs/autopilot_trace.jsonl`, ротация по размеру, пишется каждое действие,
включая наблюдательные и отказы. Поле `verified` сохраняет тройственность: `null`
означает «у действия нет читаемого состояния», и это другое утверждение, чем `false`.
Сбой записи считается, но не прерывает действие.

`dry_run` у `act_on_element`, `window_action` и `keyboard_action` разрешает цель и
классифицирует её, ничего не делая, и возвращает имя и роль разрешённого элемента —
это способ увидеть привязку до того, как она сработает.

## Состояние сессии

Инструменты сообщают о заблокированной рабочей станции явно. Без этого захват
экрана при блокировке возвращает обычный на вид кадр экрана ввода PIN-кода, и
агент не может отличить заблокированную машину от закрытого приложения или
сломанного захвата.

Определение идёт через документированный запрос состояния сессии WTS, а не через
эвристику по классам окон экрана блокировки: эти классы — деталь реализации,
менявшаяся между версиями Windows.
