# ADR-0009: Терминал читается и пишется через Класс B

- Статус: принято
- Дата: 2026-11-03
- Связано: ADR-0002, ADR-0003, ADR-0008
- Основание: замеры на conhost и Windows Terminal

## Контекст

Вождение CLI-агентов — заявленная цель проекта, а терминал в этих прогонах ни разу
не измерялся. Классификация действия для терминала решает, может ли агент работать
параллельно с человеком или обязан занимать его курсор и клавиатуру.

Измерено на двух хостах: legacy conhost (`ConsoleWindowClass`) и Windows Terminal
(`CASCADIA_HOSTING_WINDOW_CLASS`). На этой сборке Windows 11 терминалом по
умолчанию является WT, поэтому `CREATE_NEW_CONSOLE` тоже приводит в WT; conhost
пришлось запускать явно через `conhost.exe`.

Оболочка печатала маркеры, включая строку с кириллицей, так что чтение сверялось с
эталоном, а не оценивалось на глаз.

## Решение

### Чтение — `TextPattern`, работает на обоих хостах

| Хост | Класс окна | Элементов | Элемент буфера | Длина | Кириллица |
|---|---|---|---|---|---|
| conhost | `ConsoleWindowClass` | 12 | `Document` (50030) | 604 | читается |
| Windows Terminal | `CASCADIA_HOSTING_WINDOW_CLASS` | 22 | `Text` (50020) | 605 | читается |

Все три маркера найдены на обоих хостах, включая кириллическую строку. Пробелами
добито 13–18% длины, то есть содержимое настоящее, а не пустая сетка.

Тип контрола у буфера **различается** между хостами, поэтому выбирать буферный
элемент по типу контрола нельзя. Правило: буфер — это элемент с наибольшим
содержимым `TextPattern` в дереве окна; короткие значения являются заголовком
вкладки и статусным текстом.

Дерево терминала маленькое (12 и 22 элемента), поэтому обход стоит 7–16 мс и не
требует бюджета глубины из ADR-0007.

### Запись — `WM_CHAR` в дочернее окно ввода

`ValuePattern.SetValue` на терминале **принимается и ничего не делает** на обоих
хостах: `IsReadOnly` равен 0, вызов возвращает успех, маркер в буфере не
появляется. Это самый опасный вид отказа из возможных — молчаливый успех. Любая
запись в терминал обязана проверяться перечитыванием буфера.

`WM_CHAR`, отправленный в окно верхнего уровня, в conhost работает, а в Windows
Terminal — нет. Перебор маршрутов по WT:

| Цель | Способ | Дошло до оболочки |
|---|---|---|
| окно верхнего уровня | `PostMessageW` WM_CHAR | нет |
| окно верхнего уровня | `SendMessageW` WM_CHAR | нет |
| окно верхнего уровня | KEYDOWN/CHAR/KEYUP | нет |
| `DRAG_BAR_WINDOW_CLASS` | `PostMessageW` WM_CHAR | нет |
| `Windows.UI.Composition.DesktopWindowContentBridge` | `PostMessageW` WM_CHAR | нет |
| **`Windows.UI.Input.InputSite.WindowClass`** | `PostMessageW` WM_CHAR | **да** |

У WT три дочерних окна; нужное — `Windows.UI.Input.InputSite.WindowClass`, через
которое XAML-island получает ввод. Каждый маршрут проверялся уникальным маркером,
поэтому приписывание результата однозначное.

Итог: **терминал читается и пишется, не затрагивая очередь ввода сессии.**
Вождение CLI-агента — действие Класса B и может идти параллельно с работой
человека. Это не распространяется на переключение вкладок WT и на системные
сочетания самого терминала, которые остаются Классом A.

Реализация записи: найти дочернее окно по классу, послать `WM_CHAR` посимвольно,
завершить `0x0D`, затем перечитать буфер через `TextPattern` и сверить маркер.
Без перечитывания запись считать несостоявшейся.

## Буфер прокрутки — измерено, пробел закрыт

Прежняя версия этого ADR считала, что `GetText(-1)` возвращает только видимый экран,
потому что оболочка в том прогоне печатала мало строк. Замер на 2000 и 12000 строк
опроверг это.

| Напечатано строк | Возвращено строк | Диапазон номеров | Потеряно старых |
|---|---|---|---|
| 300 | 302 | — | 0 |
| 2000 | 2002 | 1–2000, непрерывно | 0 |
| 9000 | 9000 | 3–9000, непрерывно | 2 |
| 12000 | 9000 | 3003–12000, непрерывно | 3002 |

`DocumentRange.GetText(-1)` возвращает **весь буфер экрана**, а не видимую область:
видимая область составляет порядка 30 строк, а возвращено 9000. Чтение полного
буфера — 1 089 120 символов за 28–30 мс.

Буфер является кольцом высотой **9000 строк**. Это значение cmd по умолчанию на этой
машине и настраивается, поэтому в коде оно служит признаком для предупреждения, а не
жёстким законом. За пределами высоты самый старый вывод теряется безвозвратно, и
`read_terminal` сообщает `buffer_full`, чтобы агент читал буфер по мере поступления
вывода, а не один раз в конце.

Прокрутка через UIA не нужна и недоступна: у conhost `ScrollPattern` отсутствует
совсем, у Windows Terminal один элемент его имеет, но `VerticallyScrollable=0`, а
`SetScrollPercent` возвращает `0x80131509`. `GetVisibleRanges` даёт один диапазон.

Строки приходят дополненными пробелами до ширины консоли (в замере все строки ровно
120 символов), поэтому они обрезаются справа. Leading whitespace сохраняется:
отступы содержательны и в коде, и в выводе команд.

## Ловушка эха при ожидании

Оболочка печатает командную строку до её исполнения. Поэтому ожидание строки, которая
входит и в команду, срабатывает мгновенно по эху и не доказывает ничего.

Замерено: команда `ping -n 7 127.0.0.1 >nul & echo TRAP` — ожидание `TRAP` без
привязки вернуло `found=True` за **0.00 с** на первом опросе; то же ожидание с
`after_text`, равным набранной команде, заняло **6.16 с** и совпало с настоящим
выводом. Контрольный замер с маркером, которого нет в тексте команды
(`for %i in (42) do @echo RESULT_%i`), дал 2.0–2.1 с на команду длительностью
около 2 с.

`wait_terminal` поэтому принимает `after_text`: поиск начинается после последнего
вхождения этой строки. Инструмент дополнительно предупреждает, когда ожидание
вернулось быстрее 50 мс, поскольку это признак совпадения с эхом.

Отдельная ошибка, найденная при этом замере: `%R%` в cmd раскрывается при разборе
строки, до выполнения `set /a`, поэтому конструкция `set /a R=6*7 & echo %R%`
печатает пустое значение. Для маркера, которого нет в тексте команды, нужна
переменная цикла `for` — она раскрывается при выполнении.

## Что осталось неизмеренным

**Кодировка вывода.** `chcp 65001` выставлялся в самой команде. Поведение при
кодовой странице 866 не измерялось, хотя кириллица в UTF-8 прочитана корректно на
обоих хостах.

**Стабильность маршрута ввода.** `Windows.UI.Input.InputSite.WindowClass` —
внутренняя деталь реализации XAML-island. Поиск по имени класса должен
сопровождаться проверкой результата, а не предполагать успех: `write_terminal`
подтверждает запись перечитыванием буфера и сообщает «НЕ ПОДТВЕРЖДЕНО», если окно
ввода определено неверно.

**Подавленное эхо.** При вводе пароля оболочка не печатает символы, и перечитывание
не найдёт введённый текст. Для этого случая `expect` можно задать пустой строкой:
проверка вырождается в «буфер изменился» и сообщается как слабая, а не как
подтверждение.

## Последствия

`wait` для терминала заменяется перечитыванием буфера: ожидать «появления текста»
надёжнее, чем спать фиксированное время, потому что текст читается напрямую. Но
ожидание обязано быть привязанным к точке после эха команды, иначе оно подтверждает
сам факт набора, а не результат исполнения.

Предполётная проверка для терминала — не подтверждение диалога, а сверка
прочитанного маркера. Это сильнее, чем подтверждение: оно проверяет, что команда
действительно исполнена, а не что интерфейс отреагировал.

Пиксельный путь и OCR для терминалов не нужны как основной маршрут. Они остаются
запасными для случая, когда `TextPattern` недоступен.

Классификация целей в `probe_target` дополняется отдельным типом «терминал»:
маленькое дерево, буферный элемент с большим текстом, `ValuePattern` непригоден
для записи несмотря на `IsReadOnly=0`.
