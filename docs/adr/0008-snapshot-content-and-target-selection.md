# ADR-0008: Контракт семантического снимка и выбор цели по дереву, а не по заголовку

- Статус: принято
- Дата: 2026-11-02
- Связано: ADR-0001, ADR-0004, ADR-0007
- Основание: измерения спайков S3, S4

## Контекст

ADR-0001 предполагает, что семантический снимок несёт роль, имя и состояние
элемента, и что имя — надёжный идентификатор. ADR-0004 предполагает, что
получателя сообщения можно прочитать через `TextPattern`. Обе посылки проверены
на реальных окнах этой машины; обе нуждаются в поправках.

### Действия Класса B подтверждены полностью

На собственном окне в отдельном процессе, которое не было активным и было
полностью перекрыто другим окном (перекрытие подтверждено `WindowFromPoint`, а
не цветом пикселя — другие topmost-окна делают проверку по цвету ненадёжной):

- `ValuePattern.SetValue` записал текст, значение читается обратно
- `TogglePattern.Toggle` изменил состояние, `ToggleState` читается обратно
- `InvokePattern.Invoke` вызвал настоящий обработчик — подтверждено тремя
  независимыми каналами: записью в файл из обработчика, заголовком Win32 и
  `CurrentName`
- `TextPattern.DocumentRange.GetText` вернул записанный текст
- **физический курсор не сдвинулся: `(207, 1079)` до и после всех действий**

Последнее — измеренное доказательство ADR-0002: Класс B не затрагивает очередь
ввода, значит параллельность с человеком не декларация, а свойство механизма.

### Что показали реальные приложения

Обход всего дерева с чтением доступности паттернов как кэшируемых свойств:

| Приложение | элементов | с непустым Name | Text | Value |
|---|---|---|---|---|
| Firefox | 2314 | 1131 (48%) | 241 | 360 |
| AyuGram Desktop (Qt) | 1383 | 1349 (97%) | 2 | 1378 |
| Kilo (Electron) | 573 | 539 (94%) | 335 | 6 |
| Obsidian (Electron) | 295 | 187 (63%) | 163 | 2 |
| Rainmeter | 97 | 73 (75%) | 71 | 1 |
| Progman | 50 | 50 (100%) | 0 | 0 |
| Проводник (`CabinetWClass`) | 7 | 5 | 0 | 1 |
| Редактор на Java AWT | 7 | 5 | 0 | 1 |

## Решение

### Текст элемента читается из первого доступного источника

`TextPattern` и `ValuePattern` практически взаимоисключающи и зависят от
технологии: AyuGram — 1378 Value против 2 Text, Obsidian и Kilo — наоборот.
Единого источника нет. Приоритет:

`Name` → `ValuePattern.Value` → `TextPattern` → `LocalizedControlType` + `ClassName`

Снимок обязан указывать, из какого источника взято значение, потому что
доверие к ним разное.

### Флаг доступности паттерна — только намёк

Два элемента AyuGram сообщили о поддержке `TextPattern`, и оба вернули пустую
строку. Наличие флага не гарантирует читаемость, поэтому `probe_target` обязан
пробовать чтение, а не верить флагу.

### Выбор цели — по HWND или по наибольшему дереву, никогда по заголовку

У AyuGram четыре окна верхнего уровня с одинаковым заголовком `AyuGramDesktop`:
одно основное на 1383 элемента и три окна уведомлений на 0–1 элемент. Первый
прогон выбрал по совпадению заголовка окно уведомления и сделал из этого
ложный вывод о недоступности текста.

Это не артефакт спайка, а живой дефект текущего API: `get_ui_elements`
сопоставляет окна регулярным выражением по заголовку и так же попадёт в окно
уведомления. Цель выбирается по HWND, либо по паре (заголовок, класс) с
предпочтением окну с наибольшим деревом.

### Непрозрачные цели определяются по размеру дерева

Проводник и Java AWT отдают по 7 элементов при больших окнах. Эвристика:
если окно заметно больше порога по площади, а элементов меньше ~20, цель
считается непрозрачной и `probe_target` предписывает пиксельный путь с OCR.

### Идентификатор элемента не опирается на AutomationId

`AutomationId` заполнен у 0% элементов Obsidian (1 из 295), 15% Firefox, 24%
Kilo. Стабильный идентификатор снимка строится из сочетания роли, имени,
позиции и порядкового номера среди одноуровневых, а не из `AutomationId`.

### Предполётная проверка получателя читает имя элемента

В AyuGram `TextPattern` неприменим, но имена заполнены на 97% и содержат ровно
то, что нужно ADR-0004: `[List] 'Папки'`, `[ListItem] 'Улка'`, `[ListItem] 'Работа'`,
`[ListItem] 'Все чаты (112 непрочитанных чатов)'`. Проверка получателя читает
имя выбранного элемента или заголовка диалога, а не текст через `TextPattern`.

## Последствия

Формат снимка из ADR-0001 уточняется: каждый узел несёт роль, значение с
указанием источника, признак доступных паттернов, позицию, признак
нахождения вне кадра и порядковый номер.

`probe_target` становится обязательным шагом перед выбором пути, а не
опциональной справкой: он определяет, применим ли семантический путь вообще.

Текущий `get_ui_elements(window_title=...)` должен получить параметр HWND и
правило выбора при неоднозначности. Это исправление, а не новая возможность, и
оно входит в Фазу 2.

Измерения не покрывают терминалы: Windows Terminal в прогоне не был запущен,
conhost представлен только окном Java AWT. Чтение буфера терминала остаётся
непроверенным и выносится в отдельный замер.
