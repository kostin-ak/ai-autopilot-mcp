# Инструкция для ИИ-агентов: Управление рабочим столом (Desktop Autopilot)

Этот документ регламентирует правила взаимодействия агента с операционной системой через сервер `desktop-autopilot`.

---

## 1. Архитектура и запуск

Система разделена на два компонента:
1. **Фоновый демон (`autopilot_daemon.py` / `start_daemon.bat`)**: управляет прозрачным окном PyQt6 (аппаратное скрытие `WDA_EXCLUDEFROMCAPTURE`), отслеживает физические движения мыши через Win32 хуки и выполняет ввод через `SendInput`.
2. **MCP-шлюз (`mcp_server.py`)**: регистрирует инструменты в окружении агента и связывается с демоном через локальный WebSocket `ws://127.0.0.1:8765`.

### Запуск демона
Перед вызовом инструментов убедитесь, что демон активен. Если демон выключен, запустите его:
```powershell
Start-Process -FilePath "start_daemon.bat" -WindowStyle Minimized
```
Файл сессионного токена создается автоматически по пути:
`ai-autopilot-mcp/.autopilot_token`

## 2. Координатная сетка и Per-Monitor DPI

1. Скриншоты сжимаются до базовой ширины **1280 px** с сохранением пропорций монитора.
2. Все координаты `(x, y)` в вызовах инструментов передаются **относительно сжатого скриншота** (диапазон `x` от 0 до 1280).
3. Демон самостоятельно пересчитывает координаты в физические пиксели монитора с учетом Per-Monitor DPI Aware V2 (`DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2`).
4. По умолчанию на все скриншоты накладывается полупрозрачная координатная сетка (`show_grid=True`):
   - Шаг основных линий: 100 px с числовыми подписями координат по верхней и левой линейкам.
   - Засечки: каждые 50 px для точного визуального позиционирования.
5. При работе с несколькими экранах указывайте `monitor_index`:
   - `monitor_index=1`: основной дисплей (рекомендуется по умолчанию);
   - `monitor_index=0`: общий виртуальный рабочий стол всех мониторов;
   - `monitor_index=2` и выше: дополнительные мониторы.
   - Неверный индекс возвращает ошибку со списком доступных, а не молчаливый
     откат. Это намеренно: откат на `monitor_index=0` меняет масштаб кадра
     (например, с 2.0× до 3.5×), после чего все накопленные координаты
     становятся неверными без всякого признака ошибки.
   - По той же причине `monitor_index=0` непригоден для чтения текста: ширина
     4480 px сжимается до 1280. Используйте его только для обзора расположения
     окон, а для работы переходите на конкретный монитор.

## 3. Рекомендуемый рабочий цикл агента

### Шаг 1: Разведка мониторов и окон
Определите активные экраны и расположение целевых окон:
```json
// list_windows_and_monitors()
{}
```

### Шаг 2: Захват управления (ОБЯЗАТЕЛЬНО ПЕРВЫМ ДЕЙСТВИЕМ)
После выбора целевого экрана агент обязан зафиксировать захват управления. Это активирует непрерывную неоновую рамку HUD на экране пользователя:
```json
// take_control
{
  "monitor_index": 1,
  "show_grid": true
}
```
Рамка будет оставаться на экране на протяжении всей работы агента.

### Шаг 3: Поиск элементов через Accessibility
Для стандартных окон Windows запросите точные координаты элементов управления:
```json
// get_ui_elements
{
  "window_title": "Excel",
  "monitor_index": 1
}
```
Инструмент вернет координаты `click_target: [x, y]` в сетке 1280 px.

Заголовок сам по себе окно не определяет, поэтому ответ всегда сообщает, какое
именно окно выбрано и каким способом:

- `hwnd` — точный дескриптор из `list_windows_and_monitors`. Имеет приоритет и
  исключает угадывание. Используйте его, когда окно важно не перепутать.
- `resolution: "unique"` — заголовок подошёл одному окну.
- `resolution: "largest-of-N"` — заголовку соответствуют N окон верхнего уровня;
  выбрано наибольшее по площади. Так приложения с несколькими окнами под одним
  заголовком (основное плюс всплывающие уведомления) не подменяются уведомлением.
- `resolution: "win32-title"` — совпадение найдено по заголовку Win32, а не по
  UIA Name. Это разные строки для одного окна: Qt берёт UIA Name из имени
  приложения, а `GetWindowText` возвращает заголовок документа.
- `resolution: "foreground"` — параметры не переданы, взято активное окно.

Если окно не найдено, возвращается ошибка, а не пустой список: пустой список
означает, что окно найдено, но не exposes интерактивных элементов. Неверный
`hwnd` и отсутствие совпадений по заголовку различаются в тексте ошибки.

Поле `skipped_off_monitor` означает, что часть элементов лежит вне указанного
монитора и не имеет корректного `click_target`. В этом случае повторите запрос с
`monitor_index` того монитора, на котором находится окно.

### Шаг 4: Выполнение действий мышью и клавиатурой
Используйте координаты с сетки скриншота или из Accessibility:
```json
// mouse_action
{
  "action": "click",
  "x": 450,
  "y": 120,
  "monitor_index": 1,
  "show_grid": true
}
```
За 250 мс до клика демон отобразит пульсирующий маркер цели, плавно переместит курсор и дождется завершения анимаций экрана.

Для набора текста и системных клавиш используйте `keyboard_action`:
```json
// Ввод текста без конфликта раскладок RU/EN
{"text": "Пример текста для вставки"}

// Системная комбинация клавиш
{"hotkey": "ctrl+s"}
```
Текст вводится посимвольно через `KEYEVENTF_UNICODE`, а не вставкой из буфера
обмена. Буфер пользователя не затрагивается, раскладка не имеет значения, и ввод
работает там, где `Ctrl+V` не является вставкой. Буфер обмена используется как
запасной путь только для текста длиннее `CLIPBOARD_TYPING_THRESHOLD` символов.

### Шаг 5: Освобождение управления (ОБЯЗАТЕЛЬНО В КОНЦЕ ЗАДАЧИ)
Как только вся составная задача завершена, агент обязан освободить управление. Только после этого неоновая рамка HUD исчезнет с экрана:
```json
// release_control
{}
```

## 4. Протокол обработки перехвата управления человеком (`USER_OVERRIDE`)

Если человек физически сдвинул мышь более чем на 15 пикселей или нажал клавишу:
1. Демон мгновенно прерывает выполнение команды.
2. Неоновая рамка меняет цвет на янтарно-желтый.
3. Инструмент возвращает статус:
   `PAUSE: Пользователь перехватил управление мышью/клавиатурой. Спроси у пользователя в чате разрешения продолжить или уточни дальнейшие действия.`

### Правила поведения агента:
- **ЗАПРЕЩЕНО** повторно вызывать действия мышью или клавиатурой без прямого согласия человека в чате.
- **ОБЯЗАТЕЛЬНО** спросить пользователя: «Зафиксирован перехват управления. Могу ли я продолжить выполнение задачи?».
- После получения утвердительного ответа вызовите:
  ```json
  // reset_user_override()
  {}
  ```
  После этого система вернется в штатный режим.
- Человек также может самостоятельно сбросить режим паузы горячими клавишами `Ctrl + Alt + Space`.

Важно: пауза не блокирует всё. `release_control`, `reset_user_override` и
наблюдательные инструменты (`get_screen_state`, `list_windows_and_monitors`,
`get_ui_elements`, `get_hud_state`) доступны всегда. Ограничены только действия,
занимающие курсор и клавиатуру.

## 5. Состояние сессии: блокировка рабочей станции

Каждый успешный ответ содержит блок `session` с полем `locked`. Если там
`true`, в тексте инструмента первой строкой приходит предупреждение.

Причина, по которой это важно: при заблокированной станции **захват экрана
продолжает работать** и возвращает экран ввода PIN-кода. По форме ответа это
неотличимо от обычного кадра. Если увидели предупреждение о блокировке:

- не считайте снимок описанием целевой программы;
- не пытайтесь «достучаться» до приложения кликами и вводом — сессия не принимает
  ввод рабочего стола;
- сообщите человеку, что требуется разблокировка, и остановитесь.

`session.state` дополнительно различает `active`, `disconnected` и прочие
состояния; `disconnected` означает, что окна не рендерятся и захват недостоверен.

## 6. Правила выбора инструмента

Дерево доступности и действия через него предпочтительнее пикселей везде, где
цель их отдаёт: они не занимают курсор, работают по неактивным и перекрытым
окнам и не зависят от масштаба кадра.

Порядок выбора:

1. `list_windows_and_monitors` — узнать `handle`, класс и pid цели.
2. `probe_target` с этим `handle` — определить, какой путь цель вообще
   поддерживает. Классификация строится на пробном обходе, а не на числе
   элементов первого уровня: у Chromium и Electron над настоящим деревом стоит
   цепочка представлений в 4–6 уровней, поэтому окно с двумя детьми на первом
   уровне может отдавать сотни полезных узлов.
3. `get_snapshot` — семантический снимок дерева с координатами в масштабе кадра.
   Это основной путь наблюдения. Снимок намеренно неполон на больших целях:
   заголовок сообщает, какой лимит сработал, и для лимитов времени и числа узлов
   даёт токен продолжения. Передайте токен обратно, чтобы дочитать остальное.
   Усечение по глубине токеном не продолжается — увеличьте `max_depth`.
4. `resolve_clickable` — точная точка клика для того узла, по которому сейчас
   будет действие. Снимок несёт центр прямоугольника, потому что запрос точки у
   UIA стоит 162 мкс на узел; разрешать её точечно дешевле и свежее.
5. `act_on_element` — действие на узел через паттерн UIA, не занимая курсор.
   Это путь Класса B: окно не обязано быть активным или видимым, и человек может
   продолжать работать. Предпочтительнее координатных действий всегда, когда
   паттерны узла это позволяют. Каждое действие подтверждается опросом состояния,
   кроме `invoke`, у которого состояния нет — результат честно сообщается как
   «вызов принят, эффект не проверен».
6. `resolve_clickable` — точная точка клика, если координатное действие всё же
   нужно. Снимок несёт центр прямоугольника, потому что запрос точки у UIA стоит
   162 мкс на узел; разрешать её точечно дешевле и свежее.
7. Только если цель непрозрачна (`opaque` в `probe_target`) или элементов нет —
   `mouse_action`, `keyboard_action` и `scroll_screen` по координатам кадра. Все
   три являются действиями Класса A и занимают курсор или клавиатуру сессии.
8. Пауза и повторное наблюдение вместо повторных кликов наугад. Отдельного
   инструмента ожидания нет: стабилизацию кадра после действия демон выполняет
   сам, а осмысленная пауза — это повторный вызов наблюдательного инструмента.

Статус «НЕ ПОДТВЕРЖДЕНО» означает, что вызов прошёл, а состояние не изменилось.
Повторять вслепую нельзя: нужен новый снимок, потому что путь мог устареть или
элемент не поддерживает паттерн. У терминала это штатное поведение
`ValuePattern.SetValue` (ADR-0009).

Координаты в `get_snapshot` приведены к кадру указанного монитора. Если окно лежит
на другом мониторе, ответ сообщает это явно и называет правильный индекс — иначе
каждая координата выглядела бы как «вне кадра» без объяснения.

Терминал — отдельный случай (ADR-0009). Он читается через `TextPattern` и пишется
`WM_CHAR` в дочернее окно ввода, обе операции Класса B, курсор не требуется.
`ValuePattern` у терминала принимать запись не будет, несмотря на `IsReadOnly=0`,
поэтому запись всегда проверяется перечитыванием буфера.

Три инструмента для терминала:

- `read_terminal` — читает буфер. Возвращается **весь буфер экрана**, а не видимая
  область: 9000 строк, около 1,1 МБ, за 30 мс. Отдаётся срез, по умолчанию
  последние 200 строк. Есть фильтр `contains`, а также `head`, `start`/`count`.
  Буфер — кольцо высотой около 9000 строк: за её пределами старый вывод потерян
  безвозвратно, и ответ сообщает `buffer_full`. Для долгой команды читайте буфер по
  мере вывода, а не один раз в конце.
- `write_terminal` — печатает без курсора и подтверждает запись перечитыванием.
  При подавленном эхе (ввод пароля) передайте пустой `expect`: проверка вырождается
  в «буфер изменился» и сообщается как слабая.
- `wait_terminal` — ждёт появления строки вместо сна. Обязателен `after_text`, если
  ожидаемая строка входит в набранную команду: оболочка печатает командную строку до
  исполнения, и ожидание совпадёт с эхом за 0,00 с, ничего не доказав. С привязкой к
  команде то же ожидание заняло 6,16 с и совпало с настоящим выводом.

Строки буфера обрезаются справа (консоль дополняет их пробелами до своей ширины),
отступы слева сохраняются.

`wait_terminal` заменяет фиксированный сон и для сборки, и для теста, и для
установки: ждать условия быстрее и надёжнее, чем угадывать длительность.

### OCR — только для непрозрачных целей (ADR-0011)

Три инструмента: `read_screen_text`, `find_text_on_screen`, `wait_for_text`. Все три
наблюдательные, курсор не занимают и доступны при перехвате управления.

Их место в порядке выбора — после пунктов 1–6, а не вместо них. Если цель отдаёт
дерево, оно точнее, дешевле и даёт семантику. OCR нужен, когда цель непрозрачна:
содержимое Проводника, Java AWT, canvas.

Два правила, без которых OCR даёт неверные выводы:

- Распознавание идёт на **нативном** захвате, не на сжатом кадре. Замер: нативный
  1920×1080 — 76 строк и 2555 символов; сжатие до 1280 — 51 строка и 1358 символов с
  порчей текста; виртуальный рабочий стол 4480→1280 — ноль строк. Координаты
  возвращаются в пространстве кадра, так что их можно передавать в `mouse_action`.
- **Отсутствие совпадения не доказывает отсутствие текста.** Нормализация сводит
  регистр, омоглифы и пунктуацию, но не исправляет подмену отдельных букв. При промахе
  сократите строку или прочитайте экран через `read_screen_text` и посмотрите, что
  распозналось.

OCR годится для поиска и наведения, но не для чтения значений: числа, идентификаторы
и содержимое полей читаются через дерево доступности или `TextPattern`, потому что
подмена одной буквы меняет смысл, а отличить её от настоящей буквы невозможно.

`wait_for_text` с `appear=False` ждёт исчезновения текста — например, индикатора
прогресса. Это тоже замена фиксированному сну.

Признак непрозрачной цели: окно большое, а элементов меньше примерно двадцати.
Так ведут себя содержимое Проводника, приложения на Java AWT и canvas-поверхности.
Для них остаётся пиксельный путь.
